# 决策层能力与记忆系统设计（2026-08-10）

> 本文档固化决策层功能机制、搜索机制、记忆系统的完整设计讨论，
> 含业界成熟方案对照。实现前请先拍板文末"待决策事项"。
> 配套：时序一致性设计见 DESIGN_DECISION_LAYER_TIMELINE.md.docx。

## 一、能力边界原则（一切讨论的基线）

```
决策层加"定制化功能"（认知闭环、高频轻量、内联）
CLI 管"高自定义终端操作"（行动闭环、重型、委派）
```

**封顶判据（三问，全过才加）：**
1. 属于认知闭环吗？（获取信息/维持状态）
2. 高频到值得内联吗？（聊天经常用）
3. 不拖慢秒回吗？（秒级、带超时）

**核心洞察：agent 的记忆边界 = prompt 边界。**
数据不分家（消息日志全量在库），prompt 分家（build 只取当前会话）。
所有"知道什么"都是 prompt 注入策略——memory/跨会话/任务状态是同一问题的不同侧面。

## 二、现状事实（实测，2026-08-10）

### 2.1 决策层工具现状
- `_exec_tool` 仅支持 chat_history（硬编码 if-else）
- **实测：55 次决策 0 次调用 chat_history**——LLM 从不主动检索
- 更严重：LLM 曾把 `<tool>` 块当聊天文本发出去（00:50 日志实锤）
- **结论：靠 LLM 主动调工具的机制失败，已删除 chat_history**

### 2.2 删除记录（commit 待做）
- `proxy.py`：删除 `_exec_tool`，tool 分支保留协议骨架
- `tools.md` / `output_protocol.md`：删除 chat_history 段落
- `<tool>` 块协议（xml_blocks.py）保留，供未来机制使用

### 2.3 决策层零缓存
- 只有 prompt 文件 mtime 缓存（library.py / persona.py）
- 无 LLM 响应缓存、无检索缓存、无计算缓存
- **prompt caching（API 层）未被利用**：prompt 结构（静态 system + 动态 user）天然适合，预计可省 40~50% 输入费

## 三、决策层功能机制：ToolRegistry（声明式热加载）

### 3.1 架构
```
config/tools/*.yaml          ← 声明层（名称/参数/说明，热读）
src/decision/tools/*.py      ← 实现层（每工具一个模块，可热重载）
proxy.py: _exec_tool → registry.dispatch(block)
```

### 3.2 关键：工具可热更新，proxy 不可 reload
- proxy 是状态持有者（事件队列/水位/会话锁/台账），**整体 reload = 丢状态，禁止**
- 解法：工具实现从 proxy.py **移出**成独立模块 → reload 目标是无状态的工具模块
- proxy 只留"查注册表"入口，加工具不碰 proxy 代码
- 复用网关热重启基建（mtime 监视 + importlib.reload）

### 3.3 单 proxy + 多工具（不是每工具一个 proxy）
- 工具共享 proxy 的 `_reader`/`_provider`/水位/信号量
- 每工具一个 proxy = 状态分裂、循环中断、并发失效
- 多 proxy 仅存在于多账号场景（每账号一个完整 agent）

## 四、搜索机制：决策前自动预检注入（RAG 落地）

### 4.1 核心转变：从"LLM 主动调"到"系统自动注入"
```
旧（失败）：LLM 输出 <tool> → proxy 执行 → 回灌（实测 0 次调用）
新：决策前系统自动检索 → 注入【相关记忆】块 → 一次 LLM 调用消费
```

### 4.2 三层选择机制（系统决策，不靠 LLM）
```
① 召回：新消息 jieba 分词 → 检索三层记忆 → 候选集（宽）
② 精选：打分（相关 + 时效 + 实体）- 冗余惩罚 → top-k（默认 3~5）
③ 预算：记忆块 ≤ 20% prompt 预算；相关度低于阈值 → 不放（宁缺毋滥）
```

### 4.3 速度（实测估算）
- 消息库 4842 条 / 24 会话：检索 ~5-10ms
- 一次决策 2~6s（LLM 为主），记忆机制占比 <1%，不拖慢
- 50 万条时仍 <100ms（索引 + 时间窗过滤）；**L3 向量检索勿进同步路径**

### 4.4 成本模型
- 一次决策 = 一次 API 调用（无工具/无多轮时）
- 召回/选择全本地（SQLite + jieba + Python），零 API
- 记忆注入只增几百 token 输入，不增调用次数

## 五、记忆系统设计（分层 + 受限操作 + 溯源防泄漏）

### 5.1 三层记忆结构
```
L0 全局记忆：agent 本体（人设/说话风格/通用规则）—— 固定注入
L1 用户记忆：对每个用户的了解（偏好/忌讳/关系/最近话题）—— 按说话人注入
L2 会话记忆：某会话特有（群梗/成员约定）—— 按当前会话注入
L3 对话历史：消息日志（原始记录，已有）—— 按需检索
```

### 5.2 受限操作（agent 不直接编辑文件）
```
存储：workspace/memory/*.json（结构化条目）
操作：op=add / update(id) / delete(id) —— 只碰条目不碰结构
维护（系统负责）：去重（同 key 合并）、上限（每用户 N 条）、
  淘汰（旧+低置信）、冲突（新覆盖旧留 updated_at）、来源标注
```

### 5.3 注入决策（proxy 视角，一次决策一次 API）
```
LogUpdated → 差分新消息 → 召回(分词检索三层) → 精选(打分top-k)
→ 预算裁剪 → 注入【相关记忆】块 → provider.chat(唯一 API)
```

### 5.4 溯源：每条记忆带来源
```
【相关记忆】：
- [来自: 特高课 8/5] 风图: 那家店叫山城老灶
- [来自: 私聊 8/10] 风图: 我不吃辣
基础设施已有：Message.session + task_receipt 归属先例
```

### 5.5 防泄漏：三层防线
```
① 注入过滤（最强）：只注入当前会话 + 当前说话人的记忆
   → 别人的信息根本不进 prompt，无从泄露
② prompt 规则（第二道）：【信息边界】放 system，措辞强硬
   - 来自其他会话的信息仅用于理解背景，不主动复述
   - 除非用户自己提到；拿不准当作不知道
③ 输出扫描（兜底）：检测输出含非当前会话名 → 拦截
```

## 六、业界成熟方案对照（2026 调研）

| 方案 | 核心 | 与我们的对照 |
|---|---|---|
| **Letta（原 MemGPT）** | OS 式内存分页：上下文=RAM，外部=磁盘；三层记忆；自动管理 | 三层结构一致；"自动管理不靠 LLM 自觉"与实测一致；操作原语（append/replace/delete）一致 |
| **Mem0** | 结构化记忆提取：LLM 从对话提取事实，ADD/UPDATE/DELETE | 写入可用"决策后系统提取"（Mem0 模式）而非 agent 主动记 |
| **RAG 分层召回** | 粗召回→精排序→top-k 截断 | 完全一致的标准检索管线 |

**Letta 的坑（我们要避免）：**
- 自动记忆管理是黑盒 → 每条带来源/时间/置信度，可追溯
- 记忆膨胀 → 上限 + 淘汰 + 去重
- 记忆攻击 → 按说话人注入隔离（已设计）

## 七、成本优化（prompt caching，后置）

```
时机：功能/prompt 定稿后再做（prompt 一变缓存结构就变）
做法：确认 provider 支持 → 保持 system 稳定 → 读 usage.cached_tokens 观测
收益：输入费省 40~50%（system 前缀命中缓存价），零实现成本
```
