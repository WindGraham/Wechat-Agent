# 交互层（Interaction Layer）

> 三端适配器 + 运行循环组。本层只做两件事：**获取信息**和**发送信息**。
> 循环组和规则判断全部服务于这两件事。不组装 prompt、不调用 LLM、不做决策。
>
> 核心模型：**消息日志是唯一事实源**。本层是"日志同步器 + 动作执行器"——
> 决策层不接收消息内容推送，只收"某某会话日志已更新"的通知，
> 自己按版本指针差分出新增消息。

## 一、核心职责

### 1. 统一接口（本层存在的唯一理由）

```python
# 上行：日志更新通知（轻量，不带消息正文）
LogUpdated(
    session: str,
    version: int,            # 本次日志更新的版本号（每次回传 +1）
    mention_hint: bool,      # 本次更新里疑似含 @我（供决策层优先调度）
)

# 下行读取：决策层按需自取（拼 prompt 的原料）
get_context(session, n=200) -> list[Message]   # 会话历史（含 [@我]/媒体标注）
get_new_since(session, version) -> list[Message]  # 自某版本以来的新增（差分）

# 下行动作：决策层的 XML 动作包落地
submit_bundle(session, reply_blocks_xml) -> ActionResult
    # 一个包多个块如何执行——顺序、拆句间隔、引用怎么点、文件怎么发、
    # 与发现工作的屏幕互斥——全是本层内部事务，决策层无感知
    # ActionResult(ok, error, retryable, escalation_hint)
```

决策层看到的 Android 私聊和 macOS 群聊没有任何结构差异。

### 2. 端口实现（ports/，每端一份）

| 端口 | 消息来源 | 操作方式 |
|---|---|---|
| `android/` | 截图 + 本地 OCR + 区域切段识别 | ADB/root shell（随机化点击/滑动/广播输入） |
| `windows/` | 桌面微信 UI 树（UIA），截图兜底 | 原生输入事件 |
| `macos/` | Accessibility 树，截图兜底 | 原生输入事件 |

端口内部允许硬编码布局标定（一机一份）。输出必须归一化——坐标、像素、
控件树不出本层。

**端口内部是多形态策略组，不是单一实现。** 同一端的获取/操控有多种形式，
按可靠性排序、可插拔、可降级：

- Android：截图+OCR（主）/ 系统通知 dumpsys（辅助信号）/ 无障碍（微信 8.0.52+
  已屏蔽节点，仅作死路记录）
- Windows：UIA 控件树（主）/ 截图+OCR（兜底）/ 系统通知（辅助）
- macOS：Accessibility 树（主）/ 截图+OCR（兜底）/ 系统通知（辅助）

每种形态实现同一个端口接口，切换/降级对上层完全透明。

### 3. 消息日志（全系统的记忆底座）

- 每会话独立持久化（SQLite + 文本导出），msg_uid 幂等
- **回传幂等**：同一条消息无论从哪次同步进来，只入库一次
- 每次成功同步产生一个新 `version`（递增）；决策层记录自己的水位指针，
  `get_new_since` 差分出新增——**这就是"哪些消息是新的"的唯一判定方式**，
  不再需要通知正文猜测、不再需要"有人@我"胶囊点击流程
- 版本/水位之外的易失状态（已读标记等）用有界 LRU 保存，定期清理防爆

**铁律：只要进入一个会话，就必须完成一次日志更新回传才能退出。**
无论是轮询进入还是为执行动作队列进入——动作做完不许直接退，
先同步日志再退。回传失败：重试 N 次后允许退出并标 dirty，
下一轮优先重补（不允许把 agent 卡死在单个会话里）。

**多媒体打标**：同步时遇到非文字泡（图片/表情/语音/视频等），
只写入占位标记 + 裁图归档路径（打标即走，不在会话里等识别）。
文字化转换由 Proxy 在退出后按媒体转换队列限并发完成并写回日志。

### 4. 运行循环组（红点驱动，不再全量轮询）

轮询机制重设计：**首页红点/数字角标就是"该不该进会话"的唯一判据**——
有红点的会话才进入读取，没有的一律不进（消灭空转）。

```
主循环（每周期）：
  回首页 → 解析未读标记（数字红圈/免打扰红点/红色@前缀，含沉底补扫）
  → 有标记的会话：逐个进入 → 滚动读取 → 更新日志 → 回传（version+1）
    → 向决策层发 LogUpdated
  → 无标记：本轮结束（不进任何会话）
  → 空闲时：通知栏监听（近实时辅助）+ 乱逛/退避
```

- 动作执行期间屏幕被占，发现工作顺延（屏幕互斥锁，本层内部机制）
- 执行动作进入会话时，退出前同样走日志同步铁律

### 5. 统一时间序队列

通知与行动合并为**一个按时间排序的队列**，条目共两类：

| 条目 | 来源 | 含义 |
|---|---|---|
| 通知条目 | 系统通知 + 红点识别共同维护 | "该会话可能有新消息，值得进去读一次" |
| 行动条目 | 决策层 `submit_bundle` | "进入该会话执行这包动作" |

入队规则：

1. **去重不挪动**：会话 A 已在队列中，再来 A 的通知——位置不变、内容
   不更新（一个会话在队列里只占一个坑）；新会话通知追加到队尾
2. **行动吞并通知**：开始执行会话 A 的行动条目时，队列中 A 的通知条目
   直接删除——行动必然进入会话，而进会话必走日志同步铁律，
   通知的目的已被覆盖
3. **@我/主人插队**：含 @我（或来自主人）的条目直接插到队首。
   插队会话处理时，该会话其他待办也随之一起完成（见旅程规则），
   这不违反公平性——一次旅程本来就要干完这个会话的所有事

**旅程规则（处理一个条目的完整流程）：**

```
进入会话 A → 同步日志 → 执行 A 的全部待办行动
  ↓（执行期间 A 又到来新行动 → 一并吸收执行，不许中途离场）
A 的行动清空 → 最后一次日志同步 → 此时才向 Proxy 发 LogUpdated → 退出
```

- **LogUpdated 只在行动清空后发送**——否则处理到一半发出信号，
  Proxy 可能产生别会话的新行动，把本会话的尾巴和别会话更早的
  条目都搅乱
- **行动失败：有尝试次数上限**（如 2 次），耗尽后作为新条目**排到
  队尾**重试（不是丢弃——行动永远不许丢，它承载着对用户的承诺）
- 不设单会话驻留上限（暂不设计）
- **首页持续识别**：只要屏幕停在微信首页 Tab，就持续分析识别红点/
  未读（被动识别常驻，不等扫描周期）

### 6. 行为伪装

- 点击落点/滑动轨迹/等待时长/发送延迟全部随机化
- 长文本拟人分段发送、模拟打字节奏
- 目的：行为统计上像人，规避风控

### 7. 好友申请处理（2026-08-09）

好友申请不是聊天会话，走独立的 friend 流程
（`ports/android/action/friend_requests.py`）。

红点信号的生命周期（用户实测规则）：
新申请来 → 通讯录 tab 出红点；点一次通讯录 tab → tab 红点消，
但"新的朋友"入口行的头像+昵称+红点保留；点开申请详情未通过 →
入口退回纯文字"新的朋友"，红点全消（申请仍待通过）。

- **识别（两层）**：即时层——盯屏线程每帧检查首页通讯录 tab 红点
  （`contacts_tab_has_dot`，纯掩膜<5ms），新申请秒级入队；
  兜底层——队列空闲时每 `friend_check_interval`（默认 1800s）主动
  巡检一次，只负责"点开过详情但没通过"的残留态（红点全消、申请还
  在，tab 红点永远看不到）。另外三条通道同样收口：首页列表"新的
  朋友"红点（push_notify 标签重定向）、系统通知桥、以及"伪装会话"
  （新申请以昵称+打招呼出现在首页，旅程进入后落在新的朋友页时转向
  friend 流程）。乱逛不许点通讯录 tab（会把 tab 红点信号消掉但
  申请还在）
- **队列**：friend 条目（kind="friend"，会话名固定"新的朋友"），
  去重不挪动规则与 notify 相同；不进聊天旅程、不同步消息日志
- **通过**：`friend_auto_accept`（默认 true）时逐条点"查看"→
  验证页"完成"/资料页"添加到通讯录"→ 收尾弹窗，直到没有"查看"
  或达 `friend_max_accept`（默认 30）；失败按行动规则重排
- **确认纪律**：点过动作按钮后页面无可点项即视为闭环
  （资料页"发消息"OCR 不稳定，不能当唯一判据）
- 兜底巡检（probe_backstop）与手动接口共用 `probe_pending()`
  （清空后入口文案变"朋友推荐"已兼容）

### 8. 花名册与身份识别（2026-08-25）

群成员花名册落在 `workspace/group_rosters/<群名>/`（members_roster.json +
圆角头像 PNG + 资料页截图），由 `scripts/run_full_group_spider.py` 全量爬取
（导航复用生产 `WeChatTools.enter_session`：列表翻屏+搜索兜底+页面类型校验；
折叠群走 `_enter_via_folded`；小群无「更多群成员」入口时信息页即完整网格）。

- **双因子识别**（`perception/roster_matcher.py`）：头像复合分（归一化 BGR
  模板 + Hue 直方图抗偏色）≥0.70 且昵称相似度 ≥0.60 → 确认身份；
  无昵称 OCR 时头像分 ≥0.85 代偿。
- **鲁棒通道**：快速通道得分落灰区 [0.45, 0.70) 时对 top-10 候选跑
  多尺度滑窗 + 中心带复核（裁切偏移/截断/缝隙挽救，离线评测 60 人 ×
  9 种退化 0 误收）；快速通道对原图/修边图各算一次取 max（修边限 10%，
  防纯色背景头像被误修）。
- **失配调和闭环**（`perception/roster_update.py`）：`runtime.json` 的
  `roster_reconcile`（默认 true）开启时，journey 同步（`collect_group_history`
  reconcile 参数）对双因子失配消息，在其仍在屏上时点头像进资料页，
  按改名/换头像四规则调和写回花名册；定位不到的成员资料完整则作新成员
  动态学习入库。坐标映射：union 行 y → 设备行 内容顶+y（线性）；每屏限
  2 条、每轮采集限 12 条；调和后校验仍在聊天页，否则停止本次采集。
  已入库消息的 sender 不事后改（align_key 锚定依赖 sender）。

### 9. 多媒体消息处置（2026-08-25）

文字泡之外的图片/表情包/聊天记录转发卡/链接/文件卡/红包，由
`perception/media_handler.py` 统一处置。同步时对 `slice_chat` 的非 text/quote
消息，用 `classify_slice_to_task`（内部调 `media_classifier.classify_segment`）
定类型 → 构造 `MediaTask` → `MediaHandler.handle()` 点击/打开 → 按页面签名
分流取回内容 → 返回 `MediaResult`（content + raw_files + run_dir）。

- **页面签名**（`_detect_page_signature`，全帧 OCR + 返回稳定帧）：
  `chat_record` / `webview`(复制链接) / `photo_viewer` / `video_viewer` /
  `sticker_detail` / `file_card` / `media_viewer` / `unknown`。
  注意（2026-08-26 真机标定）：文件卡的「文件大小/11.9KB」在屏幕**中部**，
  顶部+底部双条 OCR 会漏，必须全帧；页面切换的过渡帧是纯黑，会被
  `media_viewer`（黑像素占比>0.25）误吞——判到黑底时等 ~1s 重截重判一次，
  后续裁切必须用返回的稳定帧。
- **链接**：进 webview → ⋯ → 复制链接 → `DeviceCtl.read_clipboard()` 直读
  （root+setuid 常驻服务，~10-20ms，见 `tools/clipboard/ClipIOServer.java`）；
  失败回退「粘贴→底部 OCR→清空」。
- **聊天记录卡**：`_read_chat_record` 滚动 OCR，`_parse_chat_record_screen`
  两遍法按时间戳/发送者/内容解析。
- **图片/视频**：`_save_photo_or_video` 长按出 action sheet，OCR 关键词
  判定图片/视频（查看器初始界面是无文字标签的 4 图标，无法预先区分）；
  **同一消息重复保存会弹「已保存过图片到系统相册/再次保存」确认框，需自动点
  「再次保存」**；取文件用「操作前快照文件名集合 → 等新名字出现」差集法
  （不能取目录最新文件，会拉到无关旧文件）→ pull → 删手机源文件 → 回会话。
- **表情包**：`_handle_sticker_detail` 裁上半屏最大非背景块。
  签名有两种变体：单曲详情页（底部「更多表情/添加」）与艺术家专辑页
  （中部「添加」+「展开全部/更多作品/艺术家主页」，2026-08-27 实测补充）。
- **文件卡**：`_handle_file` 预览页 → 右上角 ⋯ → 菜单精确匹配「保存」
  （不支持预览的类型页面只有「用其他应用打开」死路，保存入口只在 ⋯ 菜单）→
  文件落 `/sdcard/Download/WeiXin/<原文件名>` → 差集法取回 → pull → 删源。
- **红包**：仅记录，不自动点开。
- **点击前置校验**：`_verify_in_chat` OCR 顶部标题条确认在目标会话页，
  不在则拒绝点击（防首页残留状态 + 旧 bbox 乱点进别人会话）。

**接入（2026-08-27 定稿，已入轮询主链路）**：分两步——
- **内联打标（采集中，零点击）**：裁切线分段把 slice_chat 的类型传播到段
  （`cutline_segment` segs 带 `type`），`history_collect` 对非文本段用
  `classify_segment` 细分入库：content_type ∈ link/image/chat_record/file/
  red_packet，content = 占位符（"[图片]"/"[链接]"…），media_path = 裁图路径，
  `media_status=''`（messages 表新列，'' / done / failed）。无 OCR 内容的
  媒体段不再丢弃。媒体去重靠段裁图 aHash（frame_phash 列，汉明 ≤6 判同图）——
  占位符无区分度，同一发送者多张图不再互相误杀，同图跨 union 仍判重。
- **独立处置 pass（采集后，`loop/media_pass.py`）**：缝合采集中途 tap 会打断
  配准，故采集完成、屏幕停在书签处后，对待处置条目（seq 升序）用
  **存档裁图对当前屏 matchTemplate** 定位（阈值 0.85，裁图 >400px 取头部
  子条；不做 union→device 线性坐标映射）→ MediaTask → MediaHandler.handle()
  → `update_media` 按 id 精确写回（链接 URL 进 content；图片/视频/文件的
  本地路径进 media_path；聊天记录卡解析文本进 content；红包只标 done 不点击）。
  处理顺序 **seq 降序**（采集逐屏向更旧滚、逐屏 append：seq 越小物理越新，
  从书签旧侧向最新滚必须降序才顺路——seq418 实测升序会把旧目标落在身后）。
  点击位置取条带内**主内容块**中心（整行条带几何中心会落在灰底上，
  点灰底不开页——seq417 实测）。只处置**本轮采集入库**的条目
  （journey 传 since_ts=同步开始时刻；更老的在书签旧侧，滚 newer 永远找不到）。定位鲁棒性（2026-08-27 猫猫群实测
  修复）：每个位置双截屏防 fling 糊帧漏检（单截屏错过目标屏后目标沉入
  输入栏裁切区 conf 只剩 0.4）；屏面连续 2 次不变判到底提前放弃。
  单条 8 屏未命中标 failed；预算热控 `media_handle_enabled` /
  `media_handle_max_per_journey`(5) / `media_handle_timeout_s`(180)，
  剩余下轮 journey 继续。结束后 scroll_to_latest 回滚——收尾 sync 以
  「当前屏=最新屏」存书签，停在中段会污染书签。
  接入点：journey 首次 sync 成功后（动作执行前）+ collect 模式深采后。

`realtime_scan(handle_media=...)` 钩子仍在但 realtime_scan 无调用者（死代码，
待清理）。所有处置落盘 `workspace/media/{type}/{msg_id}_{ts}/`（含
manifest.json），`workspace/media/collect_debug/` 留错误现场；测试期不自动
删除；异常统一 `_return_to_chat` 回聊天页。

## 二、明确不做

- 不组装 prompt（只发 LogUpdated + 提供历史/差分读取接口）
- 不调用 LLM（多媒体标注的视觉 API 调用视为感知环节，例外）
- 不做 @我 的处理决策（@识别写进日志，处理逻辑在决策层/Proxy）
- 不包含人格文案
